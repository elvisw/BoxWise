## 成功之处

1. **Correct Course 工作流高效。** Sprint Change Proposal 一次性完成需求分析、影响评估、Epic 拆分，3 个 Story 结构清晰，无需返工。
2. **审查驱动质量。** 3 轮代码审查共发现 13 项，其中 1 项 patch（CancellationToken）、1 项 decision（LocationId 类型）、3 项 defer、7 项 dismiss。最终审查零新发现。

4. **前端组件复用。** `LocationTree` 和 `TagFilter` 直接嵌入编辑模式，无需新建组件。

## 挑战与发现

1. **EF Core InMemory 陷阱。** `.Include(i => i.CreatedByUser)` 在 EF Core InMemory 中，若 AppUser 不存在则 `FirstOrDefaultAsync` 返回 null（不是含 null navigation 的 entity）。需要显式 seed AppUser，和 `GetByIdAsync` 测试遇到相同问题。
2. **`ICollection<Tag>` 不支持 `AddRange`。** Story 文件用 `AddRange` 描述 Tags 更新，实际实现需改为 `foreach` 逐条添加。这是 API 约束，非逻辑错误。
3. **Edit 工具与 Tab 缩进冲突。** `ItemEndpoints.cs` 使用 tab 缩进，多次 Edit 操作因空格/tab 不匹配失败，最终用 Write 全文件覆写。
4. **Tag ID 名称匹配脆弱。** `ItemDto` 只有 `TagNames`（字符串），不含 `TagIds`。编辑模式通过 `TagService` 反查，重名或改名场景可能失败。这是数据设计限制，延后处理。

## 经验教训

1. **代码审查应在不同 LLM 上运行。** 实施和审查使用同一模型导致部分发现需多轮才能覆盖。理想流程：实施（模型 A）→ 审查（模型 B）。
2. **Story 文件中的代码示例应为已验证 API。** `AddRange` vs `foreach` 的差异只有在实际编译时才发现。Story 作者应验证代码片段可编译。
3. **Tab/空格一致性。** 项目部分文件使用 tab、部分使用空格。统一格式化可避免 Edit 工具问题。
4. **渐进式测试补全有效。** 先写完所有 Repository 测试，批量运行失败，再统一修复（加 AppUser seed），比逐个调试高效。
