## 关键架构决策

1. **SessionToken purpose 参数化** — `GenerateSessionToken(userId, clientIp, purpose = "2fa-setup")` 默认值保持向后兼容，modify 流程传 "2fa-modify" 15 分钟过期
2. **TOTP 双密钥窗口** — `PendingTotpSecretKey` 暂存新密钥直到 verify 确认，旧密钥在 transition 期间保持可用，防止用户因中断而锁死
3. **恢复码非消耗验证** — `ValidateRecoveryCodeAsync` 仅校验哈希不销毁，区别于登录时的消耗式 `VerifyRecoveryCodeAsync`
4. **端点独立文件** — `TwoFactorModifyEndpoints.cs` 独立于 `TwoFactorEndpoints.cs`，purpose 和生命周期不同
5. **组件复用** — `TotpSetup` / `EmailTwoFactorSetup` 加 `ModifyMode` 参数，默认 false 保持向后兼容

## 经验教训

### 成功点

1. **Spec 驱动开发流程完整验证** — bmad-spec → 审查(3轮) → bmad-create-story → bmad-dev-story → code-review → 债务清偿，全链路无跳过，流程成熟可复制
2. **Spec 审查提前发现严重缺陷** — 恢复码消耗矛盾、Email send-code 缺失、TOTP 密钥孤立三个设计缺陷在 spec 阶段修复，如果进入编码阶段将导致大量返工
3. **Edge Case Hunter 审查质量高** — 发现 5 个严重 + 8 个中等缺陷，包含真实 bug：null 守卫缺失、缓存键冲突、IP 绑定遗漏、DTO 类型错误
4. **双密钥窗口是正确模式** — "生成→确认"两步流程保留旧状态直到确认完成，任何类似场景都应采用此模式
5. **恢复码一键复制/下载** — 遗留自 Epic 8 的 UX 缺口，在 Epic 9 中低成本补齐，用户无需手动逐条抄写恢复码

### 教训

1. **Story 创建时 HTTP 方法不一致** — Story 与 modify-flow.md 之间 POST vs PUT 矛盾，评审发现并修复
2. **端点层测试标记完成但未创建** — Task 4.2 的 TwoFactorModifyEndpointsTests.cs 标记完成但实际没有创建文件，Service 层测试覆盖了核心逻辑但端点 handler 层无直接测试
3. **Story 描述表声明需精确** — "不改现有方法签名"的约束误导了代理，实际需要改 `ValidateSessionToken` 的签名（加参数），导致后续调整
4. **Story 9-1 粒度过大** — 单个 story 包含 7 个端点 + 前端对话框 + 测试 + 债务清偿，建议拆分为 2-3 个更小 story（基础 API / UI / 债务清理）
5. **审查和债务清理集中在最后阶段** — 19 条债务来自三个不同 code review 批次，集中在最后一起处理增加了风险

## 后续建议

1. **端点层测试补全** — `TwoFactorModifyEndpointsTests.cs` 仍不存在，建议后续用单独 PR 补齐
