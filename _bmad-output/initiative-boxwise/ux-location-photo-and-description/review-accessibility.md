## 高严重度

### H1 — 管理对话框与照片弹窗缺少明确的滚动容器

**位置：** `EXPERIENCE.md:188`、`215`；`DESIGN.md:130`、`159`；`.working/key-photo-dialog.html:148`、`161-168`、`171-179`；`.working/key-manage-location.html:171`、`381-418`、`507-556`。

**问题：**

- `EXPERIENCE.md:188` 只对「位置照片弹窗」写了「路径与描述换行；弹窗内容纵向滚动；关闭控件保持可见/可达；不横向滚动」。`EXPERIENCE.md:215` 也只在「触控与缩放」中提到「弹窗内容纵向滚动」。
- 「管理位置」对话框没有同样的滚动契约。新增内容（顶部提示条、名称、上级位置、三行以上描述、照片字段、已保存照片展开、本地预览、操作按钮、位置列表）会显著增加高度。
- 两张草图的 `.dialog-body` 都是 `overflow: hidden`：`key-photo-dialog.html:148`、`key-manage-location.html:171`。照片区域还使用固定高度（`key-photo-dialog.html:161-168`），底部操作区固定 50px（`171-179`）。
- 按草图直接实现时，200% 文本或 320px 宽（约 400% 缩放）下，300 字描述 + 展开的照片预览 + 提示条可能超出对话框；`overflow:hidden` 会裁剪内容。管理对话框里「保存 / 取消」在 `.dialog-body` 内，照片弹窗里路径 / 描述 / 「重试」也在 `.dialog-body` 内，这些内容可能既看不见也无法滚动到；照片弹窗的 X / 底部「关闭」在草图里位于固定头尾，仍可能可见，但这依赖实现不把整个对话框一起滚动。键盘焦点还可能移动到被裁剪的控件上。
- 静态稿是固定 390×844 的示意，不能证明滚动行为；但 `.dialog-body { overflow:hidden }` 不是手机外框的装饰，而是对话框内容区的样式，容易被实现者照抄。

**可接受的修正：**

1. 在 `DESIGN.md` 的「位置资料表单」和「位置照片弹窗」两条组件规格中明确：对话框正文是唯一的纵向滚动容器（`min-height:0; overflow-y:auto; overscroll-behavior:contain`），标题栏和底部操作区在滚动容器之外，保持固定或至少始终可达。
2. 明确「关闭控件保持可见/可达」是**无需滚动即可见**还是**可通过滚动到达**；建议至少保证 X 或底部「关闭」其中之一始终在视口内，避免长描述滚动到中段时两个关闭控件都离开视口。
3. 管理对话框的保存 / 取消在 200% 下必须可达；可以考虑底部操作区固定，或表单内保存按钮随内容滚动但提供明确可达路径。不要用嵌套滚动（描述 textarea 自身滚动 + 对话框滚动）作为唯一方案。
4. 增加一帧「长路径 + 300 字描述 + 200% / 320px」的静态或交互验证，至少覆盖：无横向滚动、关闭 / 重试 / 保存可达、焦点进入裁剪区时自动滚入视口。
5. 验收时在真实浏览器中检查 `320×640` CSS px、200% 文本缩放和横屏；静态稿不能替代。

### H2 — 保存失败 / 部分成功提示可能出现在视口外

**位置：** `DESIGN.md:161`；`EXPERIENCE.md:95`、`141-144`；`.working/key-manage-location.html:507-513`、`553-556`。

**问题：**

- 提示条固定放在「位置资料表单上方」（`DESIGN.md:161`），保存按钮在表单底部（`key-manage-location.html:553-556`）。
- 用户在窄屏或 200% 下滚到表单底部点击「保存」；失败 / 部分成功 / 结果未知的常驻提示出现在表单顶部，可能完全在视口之外。`EXPERIENCE.md:141-144` 没有规定滚动到提示、移动焦点或把提示复制到保存按钮附近。
- 部分成功还会把表单从「新建」切换为「编辑该新位置」（`EXPERIENCE.md:141`），这是一次较大的重渲染；没有规定切换后的焦点和滚动位置，键盘 / 读屏用户可能不知道状态已经变化。
- 读屏用户可能通过 live region 听到提示，但低视力键盘用户仍可能看不到；这会让「保存失败」看起来像「什么都没发生」。

**可接受的修正：**

1. 失败 / 部分成功 / 结果未知时，将焦点移到提示条（`tabindex="-1"`）或提示条内的「重试」按钮，并同时保证提示条滚入视口；不要把焦点留在已经禁用或状态不明的保存按钮上。
2. 或者在保存按钮附近增加一条简短的错误摘要（例如「保存失败，详情见上方」），与顶部常驻提示使用同一状态源，避免两处文案不一致。
3. 部分成功切换为编辑态时，明确保留滚动位置或在切换后把焦点放到表单标题 / 提示条，并播报「位置已创建，照片未上传」；不要把焦点丢到页面顶部或 body。
4. 提示条保持常驻，不自动消失（`EXPERIENCE.md:95` 已写）；「关闭提示」只应由用户主动触发，且关闭后仍能从字段状态看出照片未保存。

### H3 — 44×44 触控契约没有落到各组件规格

**位置：** `EXPERIENCE.md:195`、`215`；`DESIGN.md:54`、`158`；`.working/key-manage-location.html:114`、`222`、`238`、`263`、`308`；`.working/key-browse-location.html:118-129`、`140`；`.working/key-item-detail.html:141`；`.working/key-photo-dialog.html:113`、`181`。

**问题：**

- 契约写的是「入口、关闭、重试、保存/取消都可直接点击；触控目标至少 44×44 CSS px」（`EXPERIENCE.md:195`），并在 `215` 重复。
- 但 `DESIGN.md:54` 只给「位置照片入口」挂了 `min-target: 44px`；`DESIGN.md:158` 也只对入口写了 44px。X、底部「关闭」、重试、拍照 / 从设备选择、查看现有照片、撤销移除、重试上传、关闭提示等新控件没有逐项落到组件规格。
- 草图实际尺寸明显低于 44px：管理页 `.btn` 34px（`key-manage-location.html:222`）、`.btn-link` 30px（`238`）、提示条动作 28px（`263`）、表单动作 38px（`308`）、图标按钮 40px（`114`）；浏览页入口 40px（`key-browse-location.html:140`）、树行 32px（`118-129`）；物品详情入口 40px（`key-item-detail.html:141`）；弹窗 `.btn` 36px（`key-photo-dialog.html:181`）、图标按钮 40px（`113`）。
- WCAG 2.2 AA 的 2.5.8 最低是 24×24，28–40px 不一定构成 AA 失败；但本设计自己承诺了 44×44，且用户明确要求检查触控区。契约与视觉稿不一致，会让实现者和验收者各按一套标准。
- MudBlazor 的按钮 / 图标按钮默认尺寸也可能低于 44px；如果直接使用默认 `MudButton` / `MudIconButton` 而不覆盖，容易在真实应用里不达标。

**可接受的修正：**

1. 在 `DESIGN.md.Components` 中逐项写明 44×44 最小可点击区域：X、底部「关闭」、「重试」、「保存」、「取消」、「拍照」、「从设备选择」、「查看位置照片」、「收起」、「查看现有位置照片」、「撤销移除」、「重试上传」、「关闭提示」、行内「删除 / 取消」。
2. 明确「可点击区域」包含 padding，而不是只看文字高度；实现时用 `min-height:44px` + `min-width:44px`（图标按钮至少 44×44），并检查相邻控件间距。
3. 要么更新草图尺寸，要么在每张草图顶部标注「示意图不按 1:1 表达触控尺寸，触控尺寸以 DESIGN.md 为准」。当前 `.working` 说明只写了「不是最终视觉稿」，没有说明尺寸不可照抄。
4. 验收时用浏览器 computed box 或 DevTools 检查真实点击区域；不要用「CSS 写了 min-height」代替实际测量。树节点是既有控件，本次不要求重做，但新入口不要继承 32px 的树行高度。

## 中严重度

### M1 — 焦点返回缺少实现机制，回退目标可能不可聚焦

**位置：** `EXPERIENCE.md:187`、`207`；`DESIGN.md:178`。

**问题：**

- 契约要求关闭弹窗后「焦点回到触发入口；触发入口不存在时回到位置树当前节点或物品详情标题」（`EXPERIENCE.md:187`、`207`），方向正确。
- 但没有说明在 Blazor / MudBlazor 中如何实现：触发入口可能在对话框关闭后的重渲染中被替换，保存的 `ElementReference` 可能失效；`MudDialog` 默认的焦点恢复不一定回到业务触发按钮；「物品详情标题」如果是普通 `<h2>`，没有 `tabindex="-1"` 就不能通过程序化 `FocusAsync()` 接收焦点；树节点也需要可聚焦的引用。
- 如果只在 `OnAfterRender` 之外调用 focus，或依赖浏览器默认行为，焦点可能回到 body，键盘用户会从页面开头重新 Tab。

**可接受的修正：**

1. 在交互契约中写明：打开前保存触发元素的引用；关闭后在 `OnAfterRenderAsync` 中聚焦该元素；如果元素已不存在，聚焦一个带 `tabindex="-1"` 的标题 / 容器，而不是普通标题。
2. 为「物品详情标题」和「位置树当前节点」明确可聚焦的回退容器或聚焦 API；不要假设任意标题 / 树节点都能被程序化聚焦。
3. 把「关闭后焦点位置」列入验收：鼠标打开、键盘 Enter/Space 打开、Esc 关闭、背景点击关闭、失败后关闭，各测一次；用读屏确认焦点名称。

### M2 — 选择位置的 live region 位置矛盾

**位置：** `EXPERIENCE.md:91`、`169`、`210`、`212`。

**问题：**

- `EXPERIENCE.md:212` 要求「位置树选择变化后，浏览位置信息面板以 `aria-live="polite"` 播报『已选择 <位置名称>』；描述全文保持可导航，不强制一次朗读长文」。
- 但信息面板只在「有描述或有照片」时出现（`EXPERIENCE.md:91`），两者都无时不渲染（`169`）。如果 live region 就是面板本身，那么：两者都无时没有播报；面板每次切换都被移除 / 重新插入，播报可能丢失；如果 live region 包住整个面板，它会把 300 字描述一次性读完，和「不强制一次朗读长文」矛盾。
- 快速用方向键在树中移动时，polite 区域可能排队播报每一个节点，造成滞后或轰炸；页面初始默认选中也可能触发一次不必要的播报。

**可接受的修正：**

1. 在浏览页放一个**持久的、视觉隐藏的**状态节点（不随面板条件渲染），只播报简短状态，例如「已选择 右侧抽屉。有描述，有位置照片。」；面板本身不是 live region。
2. 对方向键快速切换做去抖，或只在选择稳定后播报；初次加载 / 默认选中不播报。
3. 描述作为普通可导航文本保留在面板中；不要让 live region 包含描述全文。
4. 同样的原则适用于表单状态条：用持久 live region，不要依赖每次重新插入的条件节点；避免 `role="alert"` 与 `aria-live` 同时挂在同一节点造成双播报。

### M3 — 已保存照片与新选照片的 alt 可能相同

**位置：** `EXPERIENCE.md:209`、`211`；`DESIGN.md:155`。

**问题：**

- `EXPERIENCE.md:211` 规定已保存照片的 `alt` 为「位置照片：<完整位置路径>」；`209` 又说管理表单内展开的预览「使用同样的 alt」。
- 编辑已有照片并选择新文件后，界面可以同时显示「新选照片（未保存）」的本地预览，以及通过「查看现有位置照片」展开的旧照片（`DESIGN.md:155`、`EXPERIENCE.md:89`）。两张不同的图片如果都叫「位置照片：<路径>」，读屏用户无法区分哪张是已保存的、哪张是未保存的。
- 这也会让「替换失败后原照片仍保留」的验收变得难以用读屏确认：用户听到两个相同名称的图片，无法确认看到的是旧图还是新图。

**可接受的修正：**

1. 使用不同的可访问名称：已保存照片为「已保存位置照片：<路径>」；新选照片为「新选位置照片预览（未保存）：<路径>」或包含文件名。
2. 每个预览连同其可见状态文字（「已保存位置照片」/「新选照片（未保存）」）放在同一个带标签的组里，确保读屏先听到状态，再听到图片。
3. 保留「加载失败时不留下破图 alt」的规则；失败态不要让旧 alt 继续暴露。

### M4 — 管理表单内的已保存照片预览没有加载 / 失败状态

**位置：** `EXPERIENCE.md:89`、`147-148`；`DESIGN.md:155`。

**问题：**

- 契约详细定义了共享弹窗的加载中、失败、重试、文件缺失（`EXPERIENCE.md:182-189`），但管理表单内的「查看位置照片」disclosure 只写了「展开 / 收起，图片只在展开时加载」（`EXPERIENCE.md:89`、`147-148`）。
- 没有定义：展开后图片加载中显示什么；加载失败显示什么；失败后是否能重试；文件缺失时是否显示破图；失败时「收起」是否仍可用；是否会自动折叠。
- 慢网络或 404 时，用户可能看到一个空白框或破图，不知道照片是「没有」「还在加载」还是「坏了」；这与弹窗的成熟失败态不一致。

**可接受的修正：**

1. 在字段内复用弹窗的三态：加载中显示进度 + 「正在加载位置照片…」；失败显示「位置照片加载失败。」+「重试」；不显示破图图标；「收起」始终可用。
2. 失败时不要自动收起，也不要清掉「已保存位置照片」的文字状态；重试成功后替换为图片，重试失败保留错误与收起。
3. 加载 / 失败用 `aria-live="polite"` / `role="alert"` 播报，但不要和弹窗的 live region 同时重复。
4. 明确图片请求只在展开时发起；收起后再次展开是否重新请求，建议沿用缓存或明确「重新加载」。

### M5 — 表单必填、上限、静态说明与动态错误的读屏信息不完整

**位置：** `DESIGN.md:153-155`；`EXPERIENCE.md:87-88`、`138`、`213`。

**问题：**

- 设计只写「名称必填」（`EXPERIENCE.md:87`、`213`），但组件规格和草图都没有可见的「必填」标记；`key-manage-location.html:386-389` 的「位置名称」只是普通标签。视力正常的用户也要等到「保存」不可用才知道名称必填。
- `EXPERIENCE.md:138` 写「名称为空或描述超过 300 字时『保存』不可用」。禁用按钮通常不可聚焦，读屏用户可能听不到它，也听不到禁用原因；这不是一个可发现的状态。
- `DESIGN.md:154-155` 把「最多 300 字」「1 张，JPG / PNG / WebP，不超过 10 MB」放在辅助说明里；`EXPERIENCE.md:213` 只明确「错误文字与字段 / 提示条关联」，没有要求把静态 helper 也放进 `aria-describedby`。读屏用户聚焦字段时可能听不到限制。

**可接受的修正：**

2. 把静态 helper 和动态错误都纳入字段的 `aria-describedby`；错误时设置 `aria-invalid="true"`。
3. 动态错误出现时用持久的 polite / alert 区域播报一次（去抖），不要逐字符播报；修正后可以清除 `aria-invalid`，但不必反复播报「已修正」。
4. 如果保留「保存」禁用，给按钮关联原因说明（例如「请先填写位置名称」/「描述超过 300 字」），或在按钮附近显示摘要；另一种更可发现的做法是保持按钮可用，提交时聚焦第一个错误字段并显示错误摘要。两种方案选其一并在契约中写死。
5. 照片格式 / 大小错误同样要播报，不能只显示在字段下方。

### M6 — 「位置照片（可选）」不是程序化字段组

**位置：** `DESIGN.md:155`；`.working/key-manage-location.html:401-406`。

**问题：**

### M7 — 弹窗失败态把重试按钮包在 `role="alert"` 内

**位置：** `.working/key-photo-dialog.html:432-437`；`EXPERIENCE.md:185`、`210`。

**问题：**

- 草图把 `role="alert"` 放在整个 `.photo-frame.failure` 上，里面同时有错误标题、说明文字和「重试」按钮。

**可接受的修正：**

1. 只把错误文本节点设为 `role="alert"`（或放进持久的 `aria-live="assertive"` 区域）；「重试」按钮作为它的兄弟节点放在 live region 外。
2. 重试时更新同一个错误节点，而不是重新插入整个块；避免 alert + 另一个 live region 双重播报。
3. 错误文本与「重试」都要保持可见、可聚焦、可点击；失败态下路径和描述仍在，X 和「关闭」仍可用。

### M8 — 信息面板位于整棵树之后，长树 / 长描述会拉远选中节点

**位置：** `DESIGN.md:128`；`EXPERIENCE.md:91`、`223`；`.working/key-browse-location.html:235-246`。

**问题：**

- 已确认的布局是「信息面板在位置树下方、同一列内」，xs 下顺序为「位置树 → 信息面板 → 标签筛选」（`DESIGN.md:128`、`EXPERIENCE.md:223`）。本评审不要求移动面板。
- 但草图只有 4 个树节点；真实家庭可能有几十个位置。选中靠近树顶的节点后，信息面板和「查看位置照片」入口可能在整棵树之后，200% 缩放下要滚动好几个视口才能看到。低视力用户可能不知道选中后下方出现了描述。
- 如果 `MudTreeView` 不是单一 Tab 停靠点，键盘用户从选中节点按 Tab 可能要穿过整棵树的每个节点才能到入口；如果是 roving tabindex，则 Tab 应直接离开树到面板。契约没有写明。
- 300 字描述在信息面板内不截断（`DESIGN.md:118`、`157`），会进一步把「按标签」和物品结果推到更下方；这不是错误，但需要在窄屏上明确滚动策略。

**可接受的修正：**

1. 保持面板在树下；明确 `MudTreeView` 使用 roving tabindex / 单一 Tab 停靠点，按 Tab 从树直接进入信息面板的入口，而不是遍历所有节点。
2. 指针选中位置后，将信息面板滚入视口（不移动焦点，或只在指针操作时滚动）；或在树的上方 / 下方提供一个简短的「已选择 X · 查看信息」链接，点击滚动到面板。不要改变已确认的面板位置。
3. 用 30 个节点 + 300 字描述在 200% / 320px 下验证：面板入口是否可达、页面是否只有一层滚动、标签筛选和物品结果是否仍可到达。
4. 如果测试发现滚动成本过高，再和用户讨论是否给描述加「展开全文」disclosure；当前契约是「不截断」，不要单方面改。

### M9 — 声称 WCAG 2.2 AA，但只覆盖 200%

**位置：** `EXPERIENCE.md:205`、`215`、`221-225`。

**问题：**

- `EXPERIENCE.md:205` 写「行为层目标 WCAG 2.2 AA」，`215` 只写「200% 缩放 / 窄屏下……不出现横向滚动」。
- WCAG 2.2 AA 的 1.4.10 Reflow 要求 320 CSS px 宽（相当于 1280px 下 400% 缩放）；1.4.4 要求 200% 文本缩放；1.4.12 要求文本间距调整后不丢内容。当前 Responsive 表只定义 xs <600、sm–md、lg+，没有 320px / 400% / 文本间距 / 横屏的验收条件。
- 草图里的 `.btn { white-space: nowrap; line-height: 1; }`（`key-manage-location.html:232`、`key-photo-dialog.html:190`）和固定高度在 200% 文本 / 1.4.12 间距下可能裁剪；没有对应测试。

**可接受的修正：**

1. 在 Responsive & Platform 或 Accessibility Floor 中增加明确的验收矩阵：320×640 CSS px（400% / 1280px）、200% 文本缩放、1.4.12 文本间距、横屏手机。
2. 验收标准写「无横向滚动、所有操作可达、焦点不被遮挡、文本不被裁剪」，并列出要测的控件（保存 / 取消 / X / 关闭 / 重试 / 入口 / 文件来源）。
3. 允许新按钮标签换行，不要用 `white-space:nowrap` 锁死；固定高度改成 `min-height`；长路径 / 长名称加 `overflow-wrap:anywhere`。
4. 如果本轮只打算做到 200%，就不要写「WCAG 2.2 AA」作为无条件目标；要么补 400% reflow，要么把目标写成「200% + 320px 宽，1.4.10 待后续验证」。

### M10 — 相机权限回退的判定路径未定义

**位置：** `EXPERIENCE.md:146`、`199`、`214`；Flow 7 `309-316`；`DESIGN.md:155`。

**问题：**

- 文案、焦点保持、`aria-live` 播报都写得很清楚：相机不可用 / 权限拒绝时显示「无法使用相机，请从设备选择照片。」，「从设备选择」保持可用。
- 但没有定义「应用如何知道相机不可用 / 权限被拒绝」。在移动浏览器上，`<input type="file" capture>` 被拒绝或取消时，常见结果是「没有文件」而不是一个可读的错误；如果实现把「用户取消」误判为「相机失败」，会错误地告诉用户相机不可用；如果真实拒绝没有触发事件，承诺的提示又可能永远不出现。
- 这会影响键盘 / 读屏用户：错误提示是否出现、焦点是否留在来源按钮组、是否还能选图，都取决于这个判定。

**可接受的修正：**

1. 明确检测路径：是用 `navigator.mediaDevices.getUserMedia` / `MediaDevices` 错误，还是用文件输入的 `change` / `cancel` 事件；只对真实可观测的权限 / 设备错误显示相机专用文案。
2. 用户取消选择时不要显示「无法使用相机」；保持原照片状态，焦点回到来源按钮组。
3. 无论相机是否可用，「从设备选择」始终可用；不要因为相机失败而禁用或隐藏它。
4. 在 iOS Safari、Android Chrome 上分别测「允许 / 拒绝 / 取消 / 无相机设备」四种情况；如果浏览器无法可靠区分拒绝与取消，就保留两个按钮和静态提示，不要断言未观察到的失败。

### L1 — 弹窗可访问名称使用视觉箭头

## 静态稿边界：哪些不是缺陷

以下内容在四张 HTML 中看起来「不可用」，但它们是静态低保真稿的预期占位，不应直接记为缺陷；真正的实现必须以 `EXPERIENCE.md` / `DESIGN.md` 的契约和真实组件为准：

- 所有操作看起来都是 `<span>`：保存 / 取消、X、底部「关闭」、「重试」、「查看位置照片」、「拍照」、「从设备选择」等（`key-manage-location.html:409-410`、`469`、`511`；`key-browse-location.html:245`；`key-item-detail.html:245`；`key-photo-dialog.html:259`、`287`、`436`）。静态稿没有 JS，不能测试键盘、焦点、文件选择或相机。
- 静态稿没有 `aria-expanded`、`aria-live`、`aria-invalid`、focus-visible 样式、disabled 语义；这些缺失是「静态视觉稿不表达行为」，不是契约缺口。
- 固定 390×844 的 `.screen`、`.phone` 外框和 `overflow:hidden` 是示意手机的画框，不能用来判断真实页面滚动；但 `.dialog-body { overflow:hidden }` 是对话框内容区本身，和 H1 的滚动契约冲突，不能照抄。
- `key-photo-dialog.html` 只有第 1 帧有 `aria-describedby`（`258`），第 2–4 帧没有（`314`、`371`、`425`）；这是静态稿内部不一致，不是实现契约。实现时应统一为「标题 `aria-labelledby` + 描述 / 路径 `aria-describedby`」。
- 草图中的图标大多没有 `aria-hidden="true"`；在真实实现中，纯装饰图标应隐藏，带文字的按钮不要让图标产生额外可访问名称。
- 草图的颜色 / 对比度是 token 声明，不是渲染测量；`DESIGN.md` 的 primary 约 5.4:1、text-secondary 约 5.7:1 的方向合理，error / success 不承载小字号正文的规则正确。静态稿不能替代真实对比度测量。

## 必须在真实应用 / 浏览器 / 读屏中验证的清单

四张静态稿不能证明以下任何一项；建议在实现后、定稿前逐项验证：

1. **缩放与重排：** 320×640 CSS px（400% / 1280px）、200% 文本缩放、1.4.12 文本间距、手机横屏；无横向滚动，保存 / 取消 / X / 关闭 / 重试 / 入口均可达。
2. **长内容：** 5 层以上且名称较长的路径；300 字带换行的描述；展开旧照片 + 新选预览 + 提示条同时存在；滚动、焦点、关闭控件。
3. **键盘：** Enter/Space 打开弹窗；Tab 在弹窗内循环；Esc 关闭；关闭后焦点回到触发入口；disclosure 用 Enter/Space 展开 / 收起，焦点留在按钮；行内删除确认可键盘完成。
4. **读屏：** NVDA + Chrome 或 VoiceOver + Safari、TalkBack + Chrome；弹窗名称 / 路径、加载中、失败重试、选择位置播报、表单错误、已保存 / 新选照片 alt。
5. **触控：** 实际 computed 点击区域 ≥44×44；相邻按钮不重叠；底部导航 / 安全区不遮挡；200% 下按钮不被裁剪。
6. **相机：** iOS Safari / Android Chrome 的允许、拒绝、取消、无相机设备；只在真实失败时显示相机文案；「从设备选择」始终可用；焦点回到来源按钮组。
7. **网络：** 慢速加载、404 / 文件缺失、重试；弹窗和表单内预览都不出现破图；路径 / 描述不因照片失败消失。
8. **Blazor 重渲染：** 弹窗关闭后的焦点恢复；live region 在条件渲染后仍能播报；部分成功切换新建 → 编辑时焦点 / 滚动 / 提示。
9. **MudBlazor 默认行为：** `MudDialog` 的 `role` / `aria-modal` / focus trap / scroll lock / 焦点恢复；`MudSnackbar` 的播报；`MudButton` / `MudIconButton` 的实际高度；`MudTreeView` 的 roving tabindex。
10. **平台返回：** Android 返回键 / 手势返回关闭弹窗而不是离开页面；关闭后筛选、滚动、焦点保留。

## 建议的修正顺序

1. **定稿前必须处理：** H1（滚动）、H2（提示可见性）、H3（44px 落规格）。这三项直接决定窄屏 / 200% 是否可用，且不需要改变已确认的布局。
2. **同批补齐：** M1（焦点返回机制）、M2（live region）、M3（alt 区分）、M4（表单内预览失败态）、M5（表单校验可访问性）。这些是读屏与键盘用户完成主流程的必要条件。
3. **实现 / 验收阶段：** M6–M10、L1–L8；其中 M8 / M9 需要在真实浏览器中用长树、长描述和 320px 验证，不能只靠文档判断。
4. **回归：** 物品照片区、位置树结构、现有筛选、删除非空限制不受影响；这些在本设计中没有被破坏，但实现后仍需按 Story 的 Verify 项复验。

## 结论

布局方向和无障碍意图整体是成熟的：按需加载、不叠第二层模态、失败可重试 / 可关闭、可见 X + 「关闭」、不靠颜色表达状态、44px 意图都值得保留。当前不能直接定稿的原因不是布局，而是**滚动容器、失败提示可见性、触控尺寸落规格**三项高严重度契约缺口，以及焦点返回、live region、alt、表单校验和表单内预览失败态这些读屏细节。建议按上面的顺序修正文档与组件规格，补一帧长内容 / 200% 验证，再在真实应用中做一次键盘 + 读屏 + 320px 回归；四张静态稿本身不能作为通过证据。
