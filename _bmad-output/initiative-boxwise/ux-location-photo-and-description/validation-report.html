审阅范围与证据边界

  • 审阅对象是设计稿：Story #1、DESIGN.md、EXPERIENCE.md、.memlog.md 与 .working/ 下四张低保真稿。未启动应用、未连接业务数据库、未在真实浏览器或读屏中操作、未做安全测试。
  • 四张 .working/*.html 是无 JS 的静态低保真稿，固定 390×844 画框，不能作为键盘、焦点、读屏、相机、滚动或 320px/200% 行为的证据。
  • 本报告是整改前快照：记录两份原件交回时的状态；之后并行的设计修订未纳入，也不依赖其输出。
  • 两份原件都只做文档层判断。无障碍原件把 gate 标为「有条件通过」，条件是先修正 H1–H3；这是对设计文档的 gate 判断，不表示设计已定稿，更不表示应用已通过验收。本报告不给出「通过」结论。

这份 spine pair 的覆盖度很高：Story #1 的五条 Requirements 全部有同名 Key Flow，状态表也把部分成功、明确失败和结果未知分开了。但它还不是一份干净的实现契约：4 个高严重度问题集中在「已确认的布局仍被标成待定」「Story 尚未写回已确认的 UX 决策」「描述是否截断两份 spine 说法相反」「表单内已保存照片预览没有失败状态」。其余问题多为精确性、重复约束和验收边界，不是范围冲突。

无障碍与窄屏评审在文档层另加 3 项高严重度：管理对话框与照片弹窗缺少明确的滚动容器、保存失败/部分成功提示可能落在视口外、44×44 触控承诺没有落到组件规格。它同时确认布局方向与无障碍意图是成熟的——按需加载、不叠第二层模态、失败可重试/可关闭、不靠颜色单独表达状态——并把已确认布局列为本轮不重开项：修正不需要重做布局。综合优先级是：先补正文滚动容器、失败/部分成功的可见反馈、触控区规格；再补焦点返回、live region、alt、表单校验与表单内预览失败态；其余留给真实应用验证。

以上都只是对设计文稿的判断，真实应用行为一律未验证。本报告不把任何真实应用项计为已通过，也不把静态稿的占位表现当作缺陷。

DESIGN.md:103, 166

4. 状态覆盖

合格

已走 IA 的四个 surface：位置管理、浏览、物品详情、位置照片弹窗。冷加载、空、保存中、完整成功、部分成功、明确失败、结果未知、字段校验、相机不可用、编辑各阶段、删除各阶段、弹窗加载/成功/失败/重试/关闭/长内容/文件缺失/离线均有覆盖。缺口集中在表单内预览、移除失败的组合状态、结果未知文案与系统返回键。

高

管理表单内已保存照片预览没有加载中/失败/重试状态（无障碍 M4 重复项，合并）

EXPERIENCE.md:89, 147-148, 200；DESIGN.md:155；review-accessibility.md M4
契约只写「图片只在展开时加载」，而共享弹窗已有加载中、失败、重试、文件缺失的完整状态。慢网络或 404 时，表单内可能只显示空白框或破图，用户无法区分「没有照片」「还在加载」「加载失败」，实现者只能自行发明行为。严重度分歧：rubric 定为 high，无障碍评审定为 medium（M4）；本报告按 high 合并列示，不重复计数。
Fix: 复用弹窗三态——加载中显示进度与「正在加载位置照片…」，失败显示「位置照片加载失败。」+「重试」，不显示破图；「收起」始终可用；失败不自动收起、不清除「已保存位置照片」状态；重试成功后替换图片，失败保留错误与收起；加载/失败用 aria-live 播报但避免与弹窗重复；明确收起后再展开是否重新请求。
中

移除照片失败的组合状态未定义

EXPERIENCE.md:112-119, 153, 156
「移除照片失败」只写「旧照片保留；提示失败；可重试」，没有说明同一次保存里已修改的描述是否已保存、表单是否留在编辑态。资料独立性 表与 编辑部分成功 只覆盖「替换失败」。
Fix: 明确「描述已保存 + 移除失败」：表单不关闭、旧照片仍可查看、描述以服务端状态为准，并给出下一步文案。
中

照片上传结果未知缺已承诺的微文案

EXPERIENCE.md:76, 142, 156
唯一的结果未知文案是新建场景的「暂时无法确认是否保存成功。请关闭表单查看位置列表；若已出现该位置……」，但此时位置和描述已保存、位置一定存在，这句话不适用；EXPERIENCE.md:142 只描述行为没有给文案，移除照片失败也没有独立文案。
Fix: 为「位置/描述已保存、照片状态未知」和「移除照片失败」各加一条固定文案，放进 Voice and Tone 与状态表。
低

弹窗的系统/浏览器返回键行为未定义（无障碍 L8 重复项，合并）

EXPERIENCE.md:44, 93, 187, 197；.working/key-photo-dialog.html:460；review-accessibility.md L8

H1 — 管理对话框与照片弹窗缺少明确的滚动容器

EXPERIENCE.md:188, 215；DESIGN.md:130, 159；.working/key-photo-dialog.html:148, 161-179；.working/key-manage-location.html:171, 381-418, 507-556
只有照片弹窗写了「内容纵向滚动」；管理对话框新增提示条、名称、上级位置、三行以上描述、照片字段、展开预览与操作按钮后高度显著增加，但两张草图的 .dialog-body 都是 overflow: hidden。200% 文本或 320px 宽下，300 字描述 + 展开预览 + 提示条可能超出对话框，保存/取消、路径/描述/重试落在裁剪区，键盘焦点还可能移到被裁剪控件上。静态稿固定 390×844，不能证明滚动行为，但对话框内容区的 overflow:hidden 不是画框装饰，容易被照抄。

H2 — 保存失败/部分成功提示可能出现在视口外

DESIGN.md:161；EXPERIENCE.md:95, 141-144；.working/key-manage-location.html:507-513, 553-556
提示条固定在表单上方，保存按钮在表单底部。用户在窄屏或 200% 下滚到底点击保存时，失败/部分成功/结果未知的常驻提示可能完全在视口之外；部分成功还会把表单从「新建」切换为「编辑该新位置」，这是一次较大的重渲染，却未规定切换后的焦点与滚动位置。读屏用户可能通过 live region 听到提示，低视力键盘用户仍可能看不到，像「什么都没发生」。
Fix: 失败/部分成功/结果未知时，将焦点移到提示条（tabindex="-1"）或其中的「重试」按钮并滚入视口；不要在保存按钮旁复制一套不一致文案，若要加摘要必须与顶部同源；部分成功切换时保留滚动位置或聚焦表单标题/提示条，并播报「位置已创建，照片未上传」；提示条保持常驻，仅由用户主动关闭，关闭后仍能从字段状态看出照片未保存。

M2 — 选择位置的 live region 位置矛盾
