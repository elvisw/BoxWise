# Decision Log — SPEC-2fa-modify-settings

## 2026-05-30: Round 3 — 审查修复

**Source:** 专项审查发现 3 个严重 + 4 个中等问题。

**Critical fixes applied:**
1. **CRIT-1 — 恢复码矛盾：** modify-flow.md 将 `method=RecoveryCode` 从 `VerifyRecoveryCodeAsync`（消耗性）改为 `ValidateRecoveryCodeAsync`（仅校验）。新增 `POST /api/auth/2fa/modify/send-code` 端点文档。
2. **CRIT-2 — Email 验证码发送缺失：** 新增 `POST /api/auth/2fa/modify/send-code` 端点，在 modify/authenticate 前向用户已配置邮箱发送验证码。
3. **CRIT-3 — TOTP 密钥孤立：** 引入双密钥窗口机制——新增 `PendingTotpSecretKey` 字段。旧密钥在 verify 确认前保持有效，中断操作可安全恢复。

**Medium issues addressed:**
- MED-1: modify-flow.md 新增 CAP-5 `modify/recovery/regenerate` 端点文档 + 数据模型变更章节
- MED-2: token 内含 email 的机制已在 send-code 端点文档中明确说明

**Medium issues noted but deferred:**
- MED-3: TOTP 多标签页竞态 — 双密钥窗口缓解了风险（旧密钥不受影响），完全解决需乐观并发控制，列为实施时注意事项
- MED-4: 5 分钟窗口过短 — 已改为 15 分钟，与 TOTP 设置流程（扫描 QR + 输入验证码）的实际耗时匹配

**Spec changes:**
- SPEC.md Assumptions 全部重写，反映实际服务端改动范围（`PendingTotpSecretKey`、`ValidateRecoveryCodeAsync`）
- modify-flow.md 端点从 5 个增加到 7 个（+send-code, +recovery/regenerate）
- 新增"数据模型变更"章节记录 `PendingTotpSecretKey` 字段

## 2026-05-30: Round 2 — CAP-5 安全修正

**Source:** 用户审查指出 CAP-5 与 CAP-2/3 同为敏感操作，不应绕过 2FA 门控。

**Changes:**
- CAP-5 验证门槛从"仅需已登录"改为"需要 modify session token"，与 CAP-2/CAP-3 统一
- Constraint 身份验证门控覆盖 CAP-5
- Non-goal 从"仅暴露已有 API"改为"仅增加 modify session token 门控"
- Assumption 更新：`regenerate` 端点需增加 session token 校验

**Rationale:** 重新生成恢复码等同于销毁用户的所有备用登录凭证。如果攻击者在已登录但未过 2FA 的情况下（如用户离开电脑未锁屏）可以重新生成恢复码，用户将失去紧急恢复能力。统一门控消除了这个攻击面。

## 2026-05-30: Initial spec creation (continued)

**Source:** 审查发现 `POST /api/auth/2fa/recovery/regenerate` API 已存在但前端无调用入口，用户无法自行更新恢复码。

**Changes:**
- 新增 CAP-5：已登录用户可直接重新生成恢复码（无需额外 2FA 验证，登录时已验证）
- 标题从"2FA 设置修改"→"2FA 设置管理"（覆盖修改 + 恢复码管理）
- Why 补充恢复码缺口描述
- Constraint 明确 CAP-5 不需要 modify session token（复用已有 API）
- Non-goal 改为"不修改恢复码生成算法和验证逻辑（仅暴露已有 API 到 UI）"
- 新增 Assumption：CAP-5 复用已有端点，服务端零改动

**Open Questions:** 无新增。CAP-5 的实现路径完全确定——仅前端改动。

## 2026-05-30: Initial spec creation

**Source:** 用户需求 — 允许用户自行修改 2FA 设置（邮箱地址、TOTP 密钥重置），无需管理员介入。

**Verdict (Pass 1 — Coherence):** All 8 Spec Law rules pass.
- 4 capabilities each have intent + success pairs.
- Constraints actually bend design: 身份验证门控 (must re-auth before modify), 方法隔离延续, 仅修改已配置方法, 速率限制, 向后兼容.
- 6 non-goals explicitly bound scope — no method removal, no new method types, no login flow changes, no standalone settings page.
- Success signal is concrete: change email → new email receives codes; reset TOTP → old key invalid.
- Lean prose throughout.

**Verdict (Pass 2 — Preservation):** User intent fully captured:
- "使用邮箱验证码、动态码和恢复码来认证后" → CAP-1 (modify/authenticate endpoint, 3 methods)
- "修改邮箱地址" → CAP-2 (modify/email + modify/email/verify)
- "重新设置TOTP应用" → CAP-3 (modify/totp + modify/totp/verify)
- "恢复码不受影响" → CAP-4 + Constraint

**Design decisions made:**
1. Modify session token 复用现有 Data Protection 机制，仅扩展 purpose 参数 — 最小化代码变更
2. 修改入口集成到 TwoFactorSetup 对话框 — 不新增页面，保持 UX 一致性
3. 验证码发送/校验复用现有 EmailTwoFactorService/TwoFactorService — DRY
4. TOTP 重置两步走（生成→验证）— 与初始设置流程一致
5. 恢复码继续有效 — 降低用户认知负担

**Assumptions:** 4 assumptions recorded. All verifiable during implementation.

**Open Questions:** 1 — 重置 TOTP 后是否需要重新生成恢复码。当前假设不需要。
